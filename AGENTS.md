# AGENTS.md

Інструкції для AI-агентів (Claude Code, Codex, Cursor, Copilot) і для людей, які працюють із
цим репозиторієм.

**Перед будь-якою зміною прочитати [ARCHITECTURE.md](ARCHITECTURE.md)** — там структура, куди що
класти, як оформлювати компоненти, сторінки, стилі, хуки й модулі, яких ще немає. Нова тека чи
файл — за його правилами; задачі немає в ARCHITECTURE.md — спершу спитати.

## Погодження рішень

Архітектурні рішення приймає власник проєкту. Агент їх **пропонує й чекає відповіді**; вигадати
й упровадити самому — заборонено, навіть якщо рішення здається очевидним чи дрібним.

**Що вважається рішенням** (потрібне «так» у чаті до першої правки):

- будь-яка залежність — нова, видалена чи оновлена, **і пакет із переліку ARCHITECTURE.md
  (розділ 1) теж**: перелік каже, *який* пакет брати, а не дозволяє ставити його без запиту;
- тека, тип файла чи модуль, якого немає в ARCHITECTURE.md, або відступ від його правил;
- новий патерн: Context і провайдер, нова категорія хуків чи утиліт, спосіб роботи з даними,
  стан поза компонентами, обхід наявного механізму (`useModal`, `lazyPage`, `PageMeta`);
- правка конфігів і збірки: `package.json`, `vite.config.ts`, `eslint.config.js`,
  `tsconfig*.json`, `index.html`, `src/main.tsx`, `scripts/`, `.github/`, `.claude/settings.json`;
- зміна правил у `AGENTS.md`, `CLAUDE.md`, `ARCHITECTURE.md`, `docs/decisions.md` — крім
  переліків «що є», які оновлюються разом із кодом (розділ «Документація — разом із кодом»).

Не рішення — робота за готовим правилом: нова сторінка за розділом 4 ARCHITECTURE.md (разом із її
рядком аліаса), секція в теці сторінки, токен теми зі значенням із макета.

**Як пропонувати.** Зупинитись перед правкою й написати в чат:

1. **Проблема** — що саме не покриває ARCHITECTURE.md чи чинне рішення.
2. **Варіанти** — 2–3, з ціною кожного (залежності, вага бандла, що зміниться в структурі).
3. **Рекомендація** — який варіант і чому.
4. **Що зміниться** — файли, документи, вплив на інші сторінки.

Далі — чекати відповіді й не робити жодної частини рішення «поки що». Після «так» — упровадити
й записати розділ у `docs/decisions.md` (що вирішили, чому, дата). Не впевнений, чи це
рішення, — вважати, що рішення, і спитати.

Частину правок із переліку вище Claude Code додатково зупиняє запитом дозволу
(`.claude/settings.json`), а відхилення від правил коду ловить `npm run lint`. Це запобіжники, а не
дозвіл: правка без запиту дозволу однаково потребує погодження, якщо вона — рішення.

## Проєкт

SPA на Vite 6.4 + React 18.3 + TypeScript (strict), React Router 7 (декларативний режим),
emotion, react-helmet-async. Збірка — `dist/` з окремим HTML і знімком
контенту на кожну сторінку.

**Мова:** код, коментарі, тексти комітів і звіти — українською. Відповідати користувачу
українською.

## Команди

```bash
npm run dev         # dev-сервер, http://localhost:5173
npm run lint        # eslint 9 (eslint.config.js), 0 попереджень
npm run typecheck   # tsc для src і vite.config.ts
npm run build       # typecheck → vite build → pages → prerender → sitemap
```

Збірці потрібен Google Chrome (пререндер). Немає Chrome — `SKIP_PRERENDER=1` для перевірки
збірки, але не для деплою.

**Перед тим як сказати «готово»:** `npm run lint` і `npm run build` проходять без помилок. Зміна
вигляду чи поведінки — ще й перевірка в браузері (`npm run dev`) на 375 px і на десктопі.

## Що НЕ робити без явного запиту

- Не додавати залежності. Дозволений перелік і версії — ARCHITECTURE.md, розділ 1; навіть із
  нього пакет ставиться лише після погодження (розділ «Погодження рішень»).
- Не створювати теки й файли «про запас»: тека зʼявляється з першим справжнім файлом.
- Не оновлювати мажорні версії (React лишається на 18 — `docs/decisions.md`), Vite, React Router,
  ESLint, TypeScript.
- Не міняти структуру тек, наявні аліаси, брейкпоінти й імена токенів теми. Новий аліас — лише
  рядок `@<Name>PageComponents/*` для нової сторінки (ARCHITECTURE.md, розділ 4).
- Не ставити тестовий фреймворк, Tailwind, CSS Modules, SCSS, UI-кіти, другий CSS-in-JS,
  бібліотеки стану.
- Не видаляти закоментований код і файли без живих посилань: це може бути тимчасово вимкнена
  функціональність. Позначити й спитати.
- Не наповнювати сторінки контентом, текстами чи стилями від себе — лише з макета або завдання.

## Інваріанти, які легко зламати

- Вміст сторінки — у теці з її іменем, однаковим скрізь: `components/AboutPage/`,
  `images/AboutPage/`, `icons/AboutPage/`, `video/AboutPage/`. Спільне для 2+ сторінок —
  у `Common/` там само; ассет чи компонент, що знадобився на другій сторінці, переїжджає в
  `Common/`. Файли ассетів — kebab-case.
- Кольори, шрифти, брейкпоінти, z-index, тривалості — лише з `theme`; літералів у компонентах
  немає.
- Аліаси — лише в `paths` у `tsconfig.json`; `resolve.alias` у `vite.config.ts` для шляхів проєкту
  не заводити.
- Модалка — `ModalWin` або власний компонент на `useModal`; блокування скролу сторінки — лише
  через `useModal`.
- Сторінка — лише `PageMeta` і склад секцій: хедер, `<main>` і футер дає `SharedLayout`. Маршрут —
  через `lazyPage`, не голий `lazy`.
- Кожна сторінка: `PageMeta` з `pagesMeta`, рівно один `h1`, рендер без дій користувача. Динамічна
  сторінка — запис у `src/utils/getPageMetaMap.ts`.
- Значення метатегів — лише через `getPageMetaTags`; новий тег у `PageMeta` — той самий тег у
  `scripts/gen-pages.mjs`.
- `<BrowserRouter useTransitions={false}>` — свідомо (видно `Loader` під час переходу). Імпорти
  роутера — з `react-router`.
- Вендорні чанки (`getVendorChunk` у `vite.config.ts`): emotion в одному чанку з React,
  `commonjsHelpers` — окремим листовим. Розділення дає «Cannot access … before initialization»
  ще до рендеру. Загального vendor-чанка не заводити.
- Барель `@/constants` — лише легкі константи; дані імпортувати напряму.
- Модулі, які виконує Node під час збірки (`utils/`, дані в `constants/`), — без `window` і
  `document` на рівні модуля; og:image — абсолютна адреса файла з `public/`.

## Документація — разом із кодом

- Новий компонент у `Common/`, хук, утиліта, константа, тека чи модуль з ARCHITECTURE.md
  (розділ 11) — у тому ж коміті оновити відповідний перелік в ARCHITECTURE.md: «Що є в
  `Common/`», таблиці тек і констант, переліки «Є:» у розділі 7.
- Нове архітектурне рішення (бібліотека, патерн, відступ від правила) — після погодження розділ у
  `docs/decisions.md` з датою: що вирішили й чому.
- У проєкті, створеному з темплейту, «темплейт» у документах означає цей проєкт: «є в
  темплейті» — є в проєкті.

## Код

- TypeScript strict, без `any` і `// @ts-ignore`. `eslint-disable` — лише точково, з поясненням.
- **Коментуємо лише неочевидне** — чому зроблено саме так, обмеження й пастки, звʼязки між
  файлами, походження магічних чисел. **Коментарі до очевидного заборонені:** переказ того, що
  робить код, повтор імені, «заготовка», історія змін («раніше…», «додав…»), розділові
  коментарі. Незрозуміло, що робить код, — перейменувати чи спростити, а не коментувати.
  Деталі — ARCHITECTURE.md, розділ 13.
- Перенесення з `newsun2`: там тека `General/` (`@GeneralComponents`) і `GeneralContainer`, тут —
  `Common/` (`@CommonComponents`) і `PageContainer`; ассети там лежать не по теках сторінок —
  класти за правилами ARCHITECTURE.md.
